## BH-01 [HIGH] quantize_notes skips notes because it re-reads the live (re-sorting) MIDI sequence while mutating it
- **Location:** `src/moshops/MoshOps.cpp:5626`
- **Verdict:** CONFIRMED (adversarial refutation failed)
- **Defect:** cmdQuantizeNotes iterates the sequence by index — `for (i=0; i<seq.getNumNotes(); ++i) { note = seq.getNote(i); ... note->setStartAndLength(...) }`. Both getNumNotes() and getNote(i) resolve through tracktion's MidiList::getSortedList(), which re-sorts whenever `needsSorting` is set. Verified in the pinned clone: MidiNote::setStartAndLength writes IDs::b (the start beat), and EventList's valueTreePropertyChanged calls EventDelegate<MidiNote>::updateObject, which returns true for IDs::b → triggerSort() sets needsSorting=true synchronously. So every note the loop moves re-orders the sorted list; on the next iteration getNote(i) returns the re-sorted element, and any not-yet-quantized note that was pushed to an already-visited index is silently skipped and never quantized. Tracktion's own bulk movers (MidiList::moveAllBeatPositions / rescale) avoid this by binding getNotes() ONCE in a range-for; cmdQuantizeNotes re-fetches every iteration.
- **Failure scenario:** A MIDI clip with division=1 beat, strength=1.0, and two notes at beats 0.6 and 0.7. i=0 quantizes the 0.6 note to 1.0, which re-sorts it AFTER the 0.7 note (list becomes [0.7, 1.0]); i=1 then reads getNote(1) = the already-moved note, and the 0.7 note (now at index 0) is never visited — it stays off-grid at 0.7. quantize_notes silently leaves some notes unquantized whenever quantization reorders neighbours (a common case: a note just-before a grid line rounding up past a note just-after it).
- **Verification:** Every link verified in the pinned tracktion clone. MoshOps.cpp:5626 iterates by index, re-calling seq.getNumNotes()/getNote(i) each pass (MidiList.h:72-73 → getNotes() → noteList->getSortedList()). getSortedList() (MidiList.h:253-267) re-sorts by beat whenever needsSorting is set. Inside the body, MidiNote::setStartAndLength writes IDs::b via state.setProperty (MidiList.cpp:759), which fires JUCE's synchronous valueTreePropertyChanged → EventDelegate<MidiNote>::updateObject returns i==IDs::b == true (MidiList.cpp:672) → triggerSort() sets needsSorting=true before the body returns. Thus the next getNote(i) reads a re-sorted array. Trace of A@0.6,B@0.7 / division=1 / strength=1: i=0 moves A to 1.0 (flips needsSorting); i=1 the list re-sorts to [B@0.7, A@1.0] and getNote(1)=A@1.0 (already done, no-op) while B@0.7 sits at the already-passed index 0 and is never quantized — exactly the claimed skip. No guard prevents it: defaults hit the case, the UndoManager doesn't defer the notification, and auto& seq holds one persistent MidiList so needsSorting carries across iterations. Decisive corroboration: tracktion's own bulk movers moveAllBeatPositions/rescale/trimOutside (MidiList.cpp:1245-1293) all bind getNotes() ONCE in a range-for, which never re-calls getSortedList() mid-loop and so is immune; cmdQuantizeNotes is the lone index-refetch deviation. Real correctness defect that occurs whenever quantization reorders neighbouring notes (a common early-note-rounding-past-later-note case).

## BH-02 [HIGH] callOnMessageThread leaks a callAsync that writes freed stack memory after a timeout
- **Location:** `src/remote/RemoteCompanionServer.cpp:754`
- **Verdict:** CONFIRMED (adversarial refutation failed)
- **Defect:** callOnMessageThread() posts a lambda to the message thread that captures the local WaitableEvent `done`, the local `result`, and the parameter `fn` (a const std::function& bound to a temporary lambda at the call site) all BY REFERENCE ([&]). It then blocks on `done.wait(timeoutMs)` (default 5000ms). On timeout it returns `err(...)` immediately WITHOUT cancelling or joining the still-queued callAsync. When the message thread later runs that lambda it executes `result = fn(); done.signal();` on `result`/`done` whose stack frame is already destroyed, and dereferences `fn` whose referent temporary is also gone — a write-after-free of stack memory plus a call through a dangling std::function. All /snapshot, /command and /take/finish companion requests route through here from the server's background thread (lines 238, 245, 361).
- **Failure scenario:** A paired phone (or the web companion) POSTs /command or /snapshot while the message thread is blocked >5s — e.g. during a synchronous cmdExportAudio render (its own watchdog allows editSeconds*8000+60000 ms), a plugin rescan driven on the message thread, or a modal file dialog. done.wait(5000) times out, callOnMessageThread returns and unwinds `done`/`result`/the call-site lambda; the message thread then finishes the export, dispatches the queued callAsync, and writes through `&result`/`&done` and calls the dangling `fn` -> heap/stack corruption or crash.
- **Verification:** Real, reachable cross-thread use-after-free. callOnMessageThread (RemoteCompanionServer.cpp:746, default timeoutMs=5000 per header:66-67) is invoked from the companion's background socket-accept thread — run() (line 177) → handleClient → handleRequest for /snapshot (238) and /command (245), which is not the message thread, so the callAsync branch (752-760) runs. It declares locals `juce::WaitableEvent done` and `juce::var result`, queues `MessageManager::callAsync([&]{ result = fn(); done.signal(); })` capturing them (and the `fn` reference parameter) by reference, then `done.wait(timeoutMs)`. On timeout it returns err() and the frame unwinds, destroying done/result and the temporary std::function bound to fn; the already-running lambda later writes `result = fn()` and `done.signal()` into that freed socket-thread stack. The timeout is genuinely hit: commandHandler = moshOps->execute (Main.cpp:164) is synchronous, and cmdExportAudio (MoshOps.cpp:7401-7451) runs a blocking render loop on the message thread with a deadline of jmax(60000, editSeconds*8000+60000) ms — a multi-minute arrangement export far exceeds the 5000 ms done.wait. Reachable: startPairing (the shipping phone/web companion) starts the listener+thread (67-77), and handleRequest only checks the auth token then forwards ANY command to execute with no command whitelist. No guard prevents it: callAsync never runs inline, the timeout fires on an independent thread while the message thread is still inside fn(), so the queued lambda completes and writes freed memory; done.signal() on a destructed WaitableEvent and the var-assignment into reused stack are UB → likely crash/corruption. Adversarial refutation attempts (whitelist, inline dispatch, guarded capture, timeout-can't-fire-while-busy) all fail against the code.

## BH-03 [MEDIUM] Duplicate color names bypass the ASTD quality-collapse clamp
- **Location:** `service/colors/runtime.py:71`
- **Verdict:** CONFIRMED (adversarial refutation failed)
- **Defect:** resolve_steers() picks `[c for c in colors if c.get('name') in reg][:3]` with NO de-duplication by name. If the same color name appears twice, both entries survive, each independently produces a steer tuple with the same peak_layer and same vec, and both are returned. Downstream (stable_audio3_cuda._steer registers one forward-hook per steer on the same transformer layer; the MLX engine sums _tf._steers), the two identical steers ADD at that layer, so the effective alpha is 2x the per-color ASTD ceiling (astd_max / the compose backoff a2/a3). This defeats the prime-directive ASTD clamp that is supposed to keep a param below quality-collapse, and the duplicate also consumes a slot in the <=3 budget, crowding out a distinct color.
- **Failure scenario:** An agent/API render request sends colors=[{name:'grit',value:100},{name:'grit',value:100}]. picked=[grit,grit], names={grit}, no_stack check passes (grit doesn't list itself). Each grit resolves to alpha=astd_max (clamped to a2=0.25 for a 2-stack), and both steers hit the same peak_layer -> effective 0.50 on that layer, ~2x past the ASTD ceiling that exists to prevent audible quality collapse.
- **Verification:** Real defect, fully traced end-to-end with no guard anywhere. resolve_steers (runtime.py:71) does `[c for c in colors if name in reg][:3]` with no name-dedup; empirically, `resolve_steers([{grit,100},{grit,100}])` returns two identical tuples (layer=14, alpha=0.25, same vec). The `names` SET (line 73) dedups only for the no_stack check, and grit's no_stack_with=[] (confirmed in colors.json — no color lists itself), so self-stacking is never rejected. Each duplicate is clamped to the a2=0.25 2-stack backoff, but there is no per-layer aggregate cap. Downstream ADD is confirmed on BOTH backends: the canonical MLX DiT (~/AI/stable-audio-3/.../dit_mlx_medium.py:277-286) loops over _steers and does an independent residual add for EACH tuple matching the block index, and the CUDA port (stable_audio3_cuda.py:144-146) registers a separate forward-hook per steer on the same block — both cases sum to 0.25+0.25=0.50 on peak_layer 14 (vs the single-grit astd_max ceiling of 0.30). The state is reachable and ungated: native set_render_param (MoshOps.cpp:5976-5988) copies up to 3 colors verbatim without dedup, cmdRenderLayer forwards them all, and _normalize_colors/the MLX adapter pass them straight to resolve_steers. This bypasses the ASTD quality-collapse clamp that resolve_steers exists to enforce, violating the 'ASTD everywhere, clamped below quality-collapse' prime directive; the duplicate also consumes one of the ≤3 slots. Only softness is that it needs a redundant/adversarial color list rather than ordinary UI use, but the agent/API command surface is a first-class ungated client.

The adapters' explicit sampwidth==3 decoders (fake_adapter.py:72, transform_adapter.py:129) confirm 24-bit inputs are expected on the per-window path, so the coverage slice path rejecting them is a genuine inconsistency. Net: a real, no-special-flags crash for the ordinary case of re-imagining a >8s MIDI/drum clip with SA3.
