# R1 adversarial review — Re-Imagine M1, DAWN Bridge, service exposure (2026-10-19)

Scope: `src/reimagine/` (ReImagineSession, ReImagineCore, ReImagineService,
plugin/ReImagineProcessor), `service/direct_render.py`, `service/server.py`, and
`src/dawn_bridge/` (PR #668), all reviewed at `origin/main` `c899b2f0`. This is a
review record, not a status claim. Nothing below was observed on the owner Mac,
in Live 11, or on an iPhone.

## Fixed in a separate PR

| # | Finding | PR |
|---|---|---|
| S1 | `service/server.py` enforced none of the documented loopback posture. It bound any `MOSH_SERVICE_HOST`, checked no `Origin` or `Host`, and parsed any Content-Type as JSON. ## Open findings (design-level, or in files an open PR already changes)

`ReImagineProcessor.cpp`, `ReImagineSession.cpp` and `direct_render.py` are changed
by open PR #790. Findings in those files are written up here instead of being
patched, so this lane does not collide with #790.

### P1. Snapshot reclamation is a Dekker pattern without seq_cst (possible use-after-free on ARM)

`ReImagineProcessor.cpp`, `publishPlayback` (≈ line 729) and `renderSelected` (≈ line 124):

```
writer (worker thread)                    reader (audio thread)
audibleSnapshot.store(new, release)       snapshotReaders.fetch_add(1, acq_rel)
while (snapshotReaders.load(acquire))…    p = audibleSnapshot.load(acquire)
ownedPlaybackSnapshot = move(new)  // frees old
```

Each side does a store followed by a load of the other side's variable. Under
release/acquire the C++ model allows each store to be reordered after the
following load (store→load reordering, which ARM64/Apple Silicon really does). One
allowed execution:

1. The writer's load reads `readers == 0`.
2. The reader increments.
3. The reader's load still returns the **old** pointer.
4. The writer frees the old snapshot.
5. The audio thread reads freed `PlaybackRegion` audio.

Trigger: any `loadSelectedTake` (keep, select, relink, reopen) while the transport
is playing. The window is a few nanoseconds, so it is rare, but it is a
use-after-free on the audio thread.

Proposed patch (four orderings, no structural change):

```diff
-    snapshotReaders.fetch_add (1, std::memory_order_acq_rel);
-    const auto* snapshot = audibleSnapshot.load (std::memory_order_acquire);
+    snapshotReaders.fetch_add (1, std::memory_order_seq_cst);
+    const auto* snapshot = audibleSnapshot.load (std::memory_order_seq_cst);
 ...
-    audibleSnapshot.store (raw, std::memory_order_release);
-    while (snapshotReaders.load (std::memory_order_acquire) != 0)
+    audibleSnapshot.store (raw, std::memory_order_seq_cst);
+    while (snapshotReaders.load (std::memory_order_seq_cst) != 0)
```

A deterministic unit test cannot prove this. It needs TSan or herd-style model
checking, and the regression evidence is the code change itself. Apply it after
#790 lands.

### P2. `prepareToPlay` reallocates `captureBuffer` while the worker may be writing it out

`prepareToPlay` (≈ line 51) calls `captureBuffer.setSize(..., keepExisting=false)`,
then `transfer.prepare(...)` and `captureWriteOffset.store(0)`. These are not
synchronized with the worker thread's `finalizeCapture` (≈ line 543), which reads
`captureBuffer`, `captureWriteOffset`, `transfer.startPpq()` and the tempo map.

Trigger: a Transfer ends (stopping the transport sets `finalizeRequested`), and the
host re-prepares before the worker finishes writing the 24-bit WAV. Live does this
on a sample-rate or buffer-size change, an audio-device switch, or freeze. The
worker then calls `writeFromAudioSampleBuffer` on a freed or reallocated buffer,
which can crash or write a corrupt source asset. A new sample rate is also mislabeled,
because `currentSampleRate` has already changed.

Proposed patch: make `prepareToPlay` wait for a pending finalize and skip the
reallocation when the shape is unchanged.

```diff
 void ReImagineProcessor::prepareToPlay (double sampleRate, int)
 {
+    // The worker may still be writing the last Transfer out of captureBuffer.
+    while (finalizationPending.load (std::memory_order_acquire) != 0 && isThreadRunning())
+        juce::Thread::sleep (1);
     const auto channels = getTotalNumInputChannels();
```

`finalizationPending` is already cleared only after `finalizeCapture` returns
(≈ line 881), so the wait is bounded by one WAV write. A Catch2 test can drive
this: arm, capture a block, stop, then call `prepareToPlay` from a second thread,
and assert the source asset hash matches the captured audio.

### P3. Render-input paths come from unvalidated hashes in saved state (low)

`takeFromVar` / region parsing (`ReImagineCore.cpp` ≈ lines 77 and 375) accept any
string as `assetHash` / `sourceHash`. Most consumers call `AssetStore::verify` first,
and a non-hex hash can never match its own SHA-256, so playback, export and relink
are safe. But `ReImagineProcessor.cpp` ≈ line 1084 (and the batch path ≈ line 1227)
opens `assets.sourceFile(inputHash)` / `renderFile(inputHash)` **without**
verifying it. A crafted Live Set with `"sourceHash": "../../../../Some/Other"` makes
the plugin read `~/Some/Other.wav` and send it to the helper as render input. The
impact is limited (a `.wav` the user can already read is processed locally), but
it breaks the content-addressed invariant.

Proposed patch: reject any non-64-hex hash when parsing state, in `ReImagineCore.cpp`
(not touched by #790):

```cpp
bool isSha256Hex (const juce::String& s) noexcept
{ return s.length() == 64 && s.containsOnly ("0123456789abcdef"); }
// in takeFromVar / region parse: if (! isSha256Hex (hash)) hash.clear();
```

Then verify the input hash at ≈ line 1084, as the batch path should too. Left here
rather than in a PR because it is low impact and changing the state parser deserves
the owner's eye on reopen compatibility.

### S2. The helper writes wherever a loopback caller says (design)

Even after #799, any **local** process can still POST `/submit` with arbitrary
`outputWav`/`manifest` paths, and the non-direct path will overwrite existing files.
`direct_render.py` already refuses occupied paths. `/loras/install` takes an arbitrary
source `path`. On a single-user Mac this is the same trust level as the user, so it is
not an escalation. It does remove the last guard if a future change exposes the helper
again.

Proposal: confine `outputWav`/`manifest` to known roots (the Re-Imagine work
directory, the app's render cache, and `tempfile.gettempdir()`) using a
`Path.resolve()` + `is_relative_to` check, and extend the direct path's "fresh
artifact paths" rule to all modes. This needs the owner to list the app-side render
directories, so it is not a drive-by patch.

### S3. `isLoopbackServiceHost` uses a prefix match (low)

`ReImagineService.cpp:166` treats any host starting with `127.` as loopback, so
`MOSH_SERVICE_HOST=127.0.0.1.example.net` passes. The value comes from the owner's
own environment, not an attacker, so the impact is low. #799 parses the host as an
IP on the Python side; the C++ check should do the same (`juce::IPAddress` round-trip,
or reject any non-numeric host other than `localhost`).

### D1. DAWN Bridge HTTP: plaintext LAN bearer token (design)

`HttpServer.mm:112` listens on `INADDR_ANY` on purpose, for the iPhone controller.
Every route except `GET /web` needs `Authorization: Bearer <256-bit SecRandom token>`.
`ScriptServer` is loopback-only with a separate secret. Both are sound for their
purpose. Residual risks:

- The token travels in cleartext HTTP, in the pairing URL fragment and on every request,
  so any passive observer on the same Wi-Fi can capture it and drive Live. Mitigations
  without TLS: rotate the token on each launch (already the case) and show a
  "controller connected from <ip>" notice. TLS or a pairing PIN is a design decision.
- `BridgeCore::authorize` compares with `isEqualToString:`, which is not constant-time.
  Timing a 256-bit token over Wi-Fi is not practical; low priority, a one-line fix if touched.
- **Unauthenticated LAN DoS:** `workerLimit = 8`, and each connection may hold a worker
  for the 2 s header deadline before auth is checked. A LAN peer that keeps 8 idle
  sockets open locks the phone out. A per-peer connection cap, or a shorter pre-auth
  header deadline (e.g. 250 ms), would bound it.

Objective-C++ / macOS only. Not built or exercised in this Linux review.

## Reviewed and found sound

- `exportVersion` file naming: `exportFileName` keeps only `[A-Za-z0-9 -_]` from the
  section label, and the asset is hash-verified before and after the copy.
- `AssetStore::relink` / `verify` / `selectedAssetsAvailable`: a traversal string cannot
  equal its own SHA-256, so verification fails closed.
- `direct_render.py`: requires hex `source_sha256`, distinct resolved paths, and
  fresh artifact paths, re-checks the source hash at render time, and validates the
  manifest and WAV frames on completion.
- `ensureRunning`: refuses a non-loopback helper host without `MOSH_SERVICE_ALLOW_LAN=1`,
  and serializes spawning with an `InterProcessLock`.
- The audio thread (`processBlock`/`renderSelected`) does no allocation, file I/O or
  locking. Generative work is on the worker thread and the service, which matches the
  tier boundary. The plugin has no Tracktion mutation, so the MoshOps invariant does
  not apply to it.
