## 2. What exists

### 2.1 Effect creation, registration, parameter access

- Tracktion registers its built-ins unconditionally in `PluginManager::initialise`
  (`plugins/tracktion_PluginManager.cpp:46-66`): volume, level meter, 4-band EQ, reverb,
  compressor, chorus, delay, phaser, pitch shift, low-pass, sampler, 4OSC, aux send/return.
  Airwindows registration is behind `TRACKTION_AIR_WINDOWS`, which defaults to `0`
  (`tracktion_engine.h:231-235`) and is not overridden anywhere in this repo's CMake.
- Mosh's palette is `kBuiltins` (`src/moshops/MoshOpsInternal.h:260-288`). `highpass` is a Mosh
  alias: Tracktion's `LowPassPlugin` created as `lowpass` and flipped with its `mode` state
  (`builtinCreationXmlType` / `effectiveBuiltinType`, same file `:290-330`).
- Creation: `cmdLoadBuiltin` (`src/moshops/MoshOps.Plugins.cpp:203-253`) —
  `edit.getPluginCache().createNewPlugin(type, {})` then `pluginList.insertPlugin`.
- Mutation: `set_plugin_param {trackId, index, paramIndex, value}` takes a **normalized 0–1**
  value (`MoshOps.Plugins.cpp:835-876`) and performs it through `SetPluginParamValueAction`
  (`:79-118`), which exists because an undone parameter write otherwise leaves
  `AutomatableParameter::currentValue` stale.
- Readback: `pluginToVar` (`src/moshops/MoshOps.cpp:3129+`) emits per parameter `index`, `name`,
  normalized `value`, and — since the Step-2B work — `display` (the engine's own
  `getCurrentValueAsString`), `unit`, and `min`/`max` where `pluginParameterPhysicalRange`
  knows them (`MoshOps.cpp:43-58`; today the low-pass frequency and four compressor params).

### 2.2 Presets

- One mechanism exists: an **instrument** preset library, `<root>/<pluginKey>/<file>`, bundled
  root `resources/presets/` (staged into the app, `CMakeLists.txt:601-606`), user root
  `~/Library/Mosh/presets`, `MOSH_PRESETS_DIR` override. `list_presets` scans it; `load_preset`
  applies a `.vital` to a hosted Vital or a `.json` to the built-in 4OSC as one undo step
  (`MoshOps.Plugins.cpp:1662-1918`). UI: `ui/src/ui/PresetPicker.tsx`, shown only on instruments.
- There is **no** effect-chain, rack or track preset, no preset versioning, and no notion of a
  preset owning a group of plugins. `docs/V3-PARITY-BRIEF-2026-09-17.md` row 7 lists presets as
  a direction gap and says the suite's audio viability is separate engine work.

### 2.3 Edit actions, undo, failure handling, persistence

- One mutation path: `MoshOps::executeImpl` (`MoshOps.cpp:651+`) → handler → `beginTxn`
  (`MoshOps.h:1068`, one Tracktion undo transaction, or coalesced into an open batch) → mutate →
  `logLine` → events → `okResult`/`errResult`.
- Failure handling is by convention: validate before `beginTxn`. Eight handlers roll back with
  `undoManager().undoCurrentTransactionOnly()` (e.g. `MoshOps.Clips.cpp:852-857`); none of them
  accounts for an open batch, where "the current transaction" is the whole batch.
- Plugin state persists as properties on the `PLUGIN` ValueTree node inside the edit file.
  A plugin constructed from a saved node comes up with each parameter at its property's value
  (`AutomatableParameter::attachToCurrentValue`, `model/automation/tracktion_AutomatableParameter.cpp:1269`;
  `ParameterWithStateValue`, `utilities/tracktion_ParameterHelpers.cpp:22-32`).
- Two known hazards in this area, both already bitten in this repo: assigning a `CachedValue`
  alone does not move the parameter the DSP reads (`MoshOps.Plugins.cpp:229-235`), and a
  `beginTxn` that records nothing makes the next undo destroy the *previous* edit.
- Guards at dispatch: the multiplayer lock scope (`src/multiplayer/LockManager.cpp`, pinned by
  `tests/golden/lock_scopes.tsv`) and the freeze guard (`MoshOps.cpp:685-720`).
- Per-track plugin commands are **not** broadcast to multiplayer peers today (only the
  master-bus ones are, `MoshOps.cpp:872-877`).

### 2.4 Recording, monitoring, render, targets

- Recording state is `transport.isRecording()`. A take is its own WAV file referenced by a
  clip (recording commands in `src/moshops/MoshOps.Record.cpp`); a track's plugin chain runs
  at playback and render time and is never printed into that file. **No existing command
  refuses a plugin-graph edit while recording.**
- A fresh track's hidden mixer elements are `[mute gate, level meter]`; the fader
  (`VolumeAndPanPlugin`) is created lazily on first touch and appended
  (`MoshOps.cpp:3115-3123`, `MoshOps.Mixer.cpp:63-116`). `load_builtin` appends to the end, so
  an effect loaded after the fader exists lands post-fader.
- Offline render: `export_audio` (`cmdExportAudio`, `MoshOps.ProjectIo.cpp:523`), all tracks plus master plugins,
  optional `sampleRate`, block size = device block size (512 headless).
- Targets: `Mosh` (the only one that hosts a track effects chain), `MoshTests`,
  `MoshDawnBridge`, the Re-Imagine VST3 and `MoshTestTonePlugin`. None of the plugin/bridge
  targets hosts track inserts, so there is nothing to check a track preset against in them.

### 2.5 Tests and gates

- `MoshTests` (Catch2) is engine-free. The engine is exercised by `--selftest`
  (`src/app/SelfTest.cpp`, with split files under `src/app/selftest/`), including an undo
  matrix and a save/reload matrix (`SelfTest.cpp:16084+`).
- UI: vitest plus `ui/src/bridge.mock.ts`; Playwright specs under `ui/e2e/`.
- Gate: `scripts/auto-loop/gate.sh native <candidate-worktree> origin/main`. Release builds
  refuse a dirty tree (`MoshSkillIdentityGate`).
- No selftest renders at more than one block size, and none measures a filter response or a
  compressor curve. No direct plugin-level DSP harness existed.

### What the compressor actually computes

`tracktion_Compressor.cpp:92-147`, per sample:

1. Detector: `sampAvg = 0.9 · lastSamp + 0.1 · |x|` (stereo: `|L + R| / 2`) — a one-pole smoothed
   **rectified average**, neither peak nor RMS. In-phase stereo reads like mono; out-of-phase
   content cancels in the detector.
2. Envelope: `currentLevel` moves toward `sampAvg` with the **attack** coefficient while
   `sampAvg > threshold` and the **release** coefficient otherwise. Each coefficient is
   `10^(log10(0.01) / (ms · sampleRate / 1000))`, i.e. the stated time is the time to settle
   within 1 %, not a time constant.
3. Gain: above threshold, `gain = outputGain · (threshold + (currentLevel − threshold) · slope) / currentLevel`
   in the **amplitude** domain. There is no knee and no mix control.

Consequences that matter for a preset:

- The stored ratio is the reciprocal slope, so a *higher* stored number compresses *less*, and
  the parameter's ceiling of 0.95 means the gentlest possible ratio is 1.053:1.
- The threshold is compared with a mean-level detector, so "−18 dB" on the label acts on
  material whose *average* rectified level exceeds −18 dB, well above where a peak-reading
  compressor with the same number would start.

### Why the 2026-09-06 calibration found "the builtin compressor does not compress"

`docs/pivot-2026-09/evidence/rehearsal-2026-09-06/ROUND1-RESULT.md` swept the normalized threshold
0.10–0.75 with normalized ratio 0.80 on a lead vocal with peak −6.2 dBFS and RMS −21.9 dBFS and
saw crest factor stay at 15.74 (15.76 at the lowest threshold). In native terms that is a ratio
slope of 0.76 — **1.3:1** — and thresholds from −19 dB upward, against a detector that reads the
signal's mean level, about −23 dB. At twice the threshold a 1.3:1 slope gives about 1 dB of
reduction, and the detector was rarely above threshold at all. The sweep moved toward *less*
compression, not more. The stepped-tone qualification in the validation report measures the
curve directly and confirms the compressor compresses as the pinned source says.

Design decisions that follow from the audit:

- **A new command, not an overload of `load_preset`.** `load_preset` is in the agent catalog
  and swaps an instrument's state. A vocal chain inserts and owns plugins and is a manual
  producer action; `load_preset` now refuses a track-chain file by name.
- **State-first application.** Each stage is built as a finished `PLUGIN` tree and added to the
  track; the only undoable action is that add. No parameter is written through the undo
  manager, so both hazards in §2.3 are out of reach and undo/redo is exact.
- **Preflight does everything that can fail**, with no engine contact, so a refusal never opens
  a transaction. The rollback that remains is defensive and handles the open-batch case the
  existing idiom does not.
- **Refused while recording.** Replacing the graph under a rolling record is not established as
  safe in this repo (§2.4), so the command says so instead of trying.
- **Pre-fader, after the user's inserts, ahead of sends and fader**, so the fader sets level
  rather than compressor drive.
- **Ownership by tag.** Re-applying finds its own group: untouched is a no-op with no
  transaction; edited or partial replaces only that group.
- **No EQ in v0.** Nothing measured justifies one before a listening pass.

## 6. Follow-on presets (planned, not built)

Same mechanism: a new JSON file, and a table row only where a new processor is needed.

- **Mosh Telephone.** `lowpass`(mode `highpass`, ~300 Hz) → `lowpass`(mode `lowpass`, ~3000 Hz).
  Needs nothing new in the table. Qualify the measured band-pass response. Compression or
  `softclip` drive only after separate qualification. It is not "Call Me Back" and makes no
  sound-alike claim.
- **Mosh Slap.** Add `delay` to the table with `feedback` (dB), `mix proportion`, and **`length`
  as typed integer-millisecond state** (it is not a parameter, and the buffer is sized in
  `initialise`, so changing it needs a graph re-initialise — verify). Insert path, a fixed
  ~90–120 ms seed, low wet level, low feedback. Never labelled tempo-synced. The latency check
  must separate wet repeats from the dry path.
- **Later, only where the existing architecture makes it straightforward:** insert `reverb`
  ambience at low wet level; a `4bandEq` presence shape after a listening pass. Doubling and
  de-essing have no qualified native processor (Airwindows is off). Phrase-specific echo throws
  need send and automation work.
