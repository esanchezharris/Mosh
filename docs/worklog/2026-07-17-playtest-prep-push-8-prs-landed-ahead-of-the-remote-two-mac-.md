**Playtest-prep push — 8 PRs landed ahead of the remote two-Mac playtest (2026-07-17, #345–#350, #353, #354-pending).** A 42-finding bug sweep of the multiplayer/generative surface fed a merge-ordered batch: **#345** SA3/preview engine-badge honesty + `docs/TESTER_QUICKSTART.md`; **#346** the guest zip pipeline (`scripts/playtest/package-guest-zip.sh` reuses `run-mosh.sh`'s real bundle/sign functions against a staging copy, plus `setup-guest.sh` one-command real-model install and `collect-diagnostics.sh`); **#347** self-healing MP stems (`mp_fetch_missing_stems` + a SHA-256 download-integrity check + a blob store on the local dev relay so the whole round-trip is hermetic under `--selftest`); **#348** bounded plugin-scan (background thread + dead-man's-pedal blacklist + progress events, FIT-003 — independent of the sweep); **#349** service-spawn de-freeze (early-bail when the child died instead of riding out a ~30s warmup, closing 4 duplicate sweep findings at once); **#350** discoverable v2 multiplayer Create/Join with a persistent room code + a confirm dialog gating join-replaces-project; **#353** guest graceful degradation (honest capability-gated errors/menu items, export-reveal, demo-mode labeling). **#354** (async stem transfer off the message thread) is open/mergeable, not yet landed — it removes the brief freeze during audio-clip sync, behind a `MOSH_MP_SYNC_TRANSFER` kill switch. The pre-merge review pass caught two defects invisible to the test suites (mock backends resolve instantly, so vitest/e2e never exercised the real synchronous cost): (1) an eager `loadCapabilities()` call added to `init()` issued `list_transform_targets`, whose native handler spawns the generative service **synchronously on the message thread** (`execute_command` is NOT threaded the way `brain_chat` deliberately is) — a guaranteed ~1.3–2s freeze on **every launch** for owner and guest alike, fixed by moving the fetch to the same lazy, action-scoped trigger points `loadColors`/`loadTransformTargets` already used; (2) `uploadBlob`/`downloadBlob` had no HTTP-status or SHA-256 integrity checks — a rejected/truncated transfer could read back as a false success (`downloadBlob`'s SHA-256 verify landed in #347; `uploadBlob`'s HTTP-status check is part of the still-open #354).
