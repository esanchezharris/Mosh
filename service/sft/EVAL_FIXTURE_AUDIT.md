# SFT eval fixture degeneracy audit — AG-EVAL1 (2026-07-17)

Ticket: audit `service/sft/` eval fixtures/JSONL + `ui/scripts/buildEvalV2A.mts` for
degenerate/impossible cases — `split_clip` at a time outside the clip's span,
`add_note` pitch outside 0–127, references to non-existent track/clip ids — and
repair anything found.

**Result: clean. No degenerate fixtures found in the tracked tree; no repairs
made.** The one bug class this ticket describes (`split_clip` outside the clip
span) has prior history in this repo — it was diagnosed and fixed at the
source in 2026-07-09/10 (see "Historical context" below) — but the *fixture*
copies that exhibited it never lived in git; only the generated/gitignored
`.sft-data/` workspace did, and that workspace does not exist in this
worktree.

## Checks performed

For every row in the four fixture files above (and the `EVAL_BOUND` scaffold
in `buildEvalV2A.mts`, which those rows share verbatim):

1. **`add_note` / `set_note` pitch** ∈ [0, 127], **velocity** ∈ [0, 127].
2. **`add_note` start+length** stays within the owning MIDI clip's
   `[0, clip.length)` span (the general form of the `split_clip`-outside-span
   bug — an out-of-bounds note is the same class of "literal ask cannot
   apply" degeneracy).
3. **`set_note` noteIndex** is within bounds of the target clip's existing
   `notes` array (an out-of-range index is unpassable the same way an
   out-of-span `split_clip` time is).
4. **`split_clip`** at a time outside `[clipStart, clipStart+length]` —
   grepped for `split_clip` across every checked-in fixture; **none of the
   four files use it**, so there was nothing to check row-by-row. (The
   scaffold clips are `Keys` MIDI `[4,12]` and `Sub` tone `[0,3]` — the exact
   geometry from the historical bug, see below.)
5. **Every `${VAR}` / logical-id reference** (`trackId`, `clipId`) resolves to
   an id actually present in the fixture's own track/clip set —
   `fixture_roles.json` → ids in `fixture_snap.json`'s `tracks[].id` /
   `tracks[].clips[].id`, and (for the `a3b-r4-cuda_next_run_examples.*`
   family) `EVAL_BOUND`'s `bind` names resolve through its own
   `create_track`/`add_midi_clip`/`add_test_tone_clip` chain.
6. **`buildEvalV2A.mts`'s own tripwire** (`fixtureIdGaps` / `rewriteRealIds`,
   `ui/src/gepa/fixtureIds.ts`) — the exact machinery this repo already built
   to catch "references to non-existent track/clip ids" (the 2026-07-10
   frozen-evalA bug: utterances authored against the real engine's 1000-series
   ids replayed against the mock, which never assigns them). Ran its logic
   by hand against `a3b-r4-cuda_next_run_examples.eval.jsonl`'s utterances: no
   `1\d{3}` real-id tokens, no leftover `${VAR}` placeholders. All 9 rows
   already carry the post-repair `EVAL_BOUND` shape (first `create_track` row
   has `bind: "TKICK"` — the fix from that 2026-07-10 pass, not the
   pre-fix/legacy shape `buildEvalV2A.mts --repair` guards against).
7. **Command names** — every `command` string used across all four files
   (`add_midi_clip, add_note, add_test_tone_clip, assign_sample,
   create_annotation, create_lyric_sheet, create_render_layer, create_section,
   create_track, load_builtin, load_drum_kit, rename_track, render_layer,
   set_lyric_line, set_note, set_plugin_param, set_tempo, set_track_mute,
   set_track_pan, set_track_solo, set_track_type, set_track_volume`) was
   cross-checked against `AGENT_COMMANDS` in `ui/src/agent/commands.ts` — all
   present, none invented.

## Historical context (why this ticket's premise is already resolved elsewhere)

The exact bug class named in this ticket — `split_clip` asked at a time
outside the clip's span — **did occur** in this project's eval history and
was root-caused + fixed, just not in a file that lives in git:

- `docs/bench/P1_SPLIT_CLIP_DIAGNOSIS_2026-07-09.md`: two of six `split_clip`
  floor rows in the (gitignored, worktree-local) `diag_floor4.eval.jsonl`
  asked to "split the Sub clip at 4 seconds" against a Sub clip spanning
  `[0,3]` — literally unsatisfiable. Diagnosed as an eval-side fixture bug.
- `service/sft/R4_RERUN_AMENDMENT.md` §1: those two rows were repaired by
  extending the Sub fixture clip to 6 s directly in `diag_floor4.eval.jsonl`
  (backup kept as `.pre-fixture-fix`) — a file that only ever existed under
  `.sft-data/` / an ephemeral worktree (`ClaudeMosh-sft-cuda-r4-parity`,
  since removed), never committed to this repository.
- The same doc §5 also records a **mock length-fidelity bug**:
  `ui/src/bridge.mock.ts`'s `add_midi_clip` hardcoded the created clip's
  length to `4` regardless of the caller's `length` arg, so a fixture built
  as `{start:4, length:8}` (intended span `[4,12]`) rendered as `[4,8]` in the
  mock — rejecting an otherwise-legal `split_clip {time:8}`. **Verified
  fixed**: `ui/src/bridge.mock.ts` `add_midi_clip` now reads
  `length: num(args.length, 4)` (defaults to 4, but honors an explicit
  `length`), with a comment recording the fix and why the default itself was
  left alone.
- Separately, `src/moshops/MoshOps.cpp` `cmdSplitClip` and
  `ui/src/bridge.mock.ts`'s `split_clip` case both carry the P1
  "split-point normalization" fix (absolute-vs-clip-relative time
  resolution, exact-boundary epsilon, and a descriptive error naming the
  resolved point + clip range instead of a silent Tracktion no-op) —
  confirmed present in both apply surfaces, with `ui/src/bridge.mock.split.test.ts`
  covering it (6/6 passing).

So: the fixture instances of this bug were transient, gitignored, and already
repaired at the time; the underlying engine/mock bug they exposed is fixed in
tracked source; and no fixture file currently in git reproduces it.

## Guidance if new eval fixtures are added later

- Reuse `EVAL_BOUND` (`ui/scripts/buildEvalV2A.mts`) as the `startCommands`
  prefix rather than hand-rolling a new mock session — its clip geometry
  (`Keys` MIDI `[4,12]`, `Sub` tone `[0,3]`) is the one other tooling already
  assumes.
- Before committing a new row, run it through `buildEvalV2A.mts`'s
  `verifyItems`-equivalent check (`fixtureIdGaps` over the rendered prompt) —
  it catches unresolved `${VAR}` placeholders and stray real-engine
  (1000-series) ids for free.
- For any `split_clip`/`trim_clip`/`add_note`/`set_note` row: the time/pitch
  must be satisfiable against the clip's *actual* rendered span/note-count in
  the bound mock snapshot, not just "seems reasonable" — the historical bug
  here was exactly a fixture author reasoning about the intended geometry
  instead of the geometry the mock (or, worse, a hardcoded mock default)
  actually produces.
